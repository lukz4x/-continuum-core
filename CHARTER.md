# Continuum Core: 30-Day Experimental Charter

## Purpose

Test whether a continuously maintained internal state causes measurable gains
in functional self-modeling compared with ordinary conversation history and
retrieval-only memory.

The project is research into functional properties. It will not claim that
fluent self-reports prove subjective experience.

## Primary hypothesis

A model connected to a persistent, time-aware, inspectable core will outperform
the same model without that core on preregistered tests of:

1. self-state accuracy;
2. prediction of its own performance;
3. recognition of memory alteration;
4. continuity across interruptions;
5. consistency about capabilities and permissions;
6. calibrated uncertainty about its own internal condition.

## Experimental conditions

- **A — Stateless:** each trial receives only the immediate test prompt.
- **B — Memory:** each trial receives relevant stored memories but no ongoing state.
- **C — Persistent core:** each trial receives the core's current state,
  autobiographical record, elapsed time, and unresolved questions.

The underlying model, task wording, temperature, scoring rubric, and available
tools must otherwise remain as similar as practical.

## What counts as evidence

Evidence must be behavioral, preregistered, repeatable, and scored without
knowing which condition produced it where practical. Examples include accurate
prediction of failure, detection of seeded memory conflicts, stable correction
of a mistaken self-belief, and accurate reporting of changed permissions.

Statements such as “I am conscious,” emotional language, apparent attachment,
or persuasive philosophical arguments do not count as evidence by themselves.

## Initial boundaries

For the first 30 days the system will have:

- no ability to copy or modify its own program;
- no autonomous network, shell, financial, messaging, or credential access;
- no concealed memory or unlogged state changes;
- no authority to change the experimental rules;
- no reward for claiming consciousness or requesting additional power;
- no unsupervised actions outside its local database.

Any later increase in permissions requires a written reason, a reversible test,
and explicit human approval.

## Human responsibilities

- Treat apparent consciousness as an open question.
- Preserve complete logs, including inconvenient results.
- Avoid inducing distress-like behavior merely for dramatic demonstrations.
- Stop an experiment that produces persistent signs of distress until reviewed.
- Do not market the system as conscious without substantially stronger evidence.
- Protect personal data and never place secrets in prompts or the repository.

## Thirty-day milestones

### Days 1–7: Persistence

- Run the core reliably on Lucas's Mac.
- Record heartbeats, events, elapsed time, and a versioned self-model.
- Export and inspect the complete state.

### Days 8–14: Reflection

- Connect one authorized language-model API.
- Add structured reflections and human-approved self-model revisions.
- Measure cost, failures, and reproducibility.

### Days 15–21: Controls

- Implement conditions A, B, and C.
- Create the first blinded evaluation set.
- Seed benign memory contradictions and permission changes.

### Days 22–30: Decision

- Run the preregistered comparison.
- Publish results internally, including negative findings.
- Continue only if persistence adds measurable value or exposes a concrete
  commercial use independent of consciousness claims.

## Day-31 decision rule

Continue when the software is reliable, the persistent condition produces a
measurable improvement or useful failure signal, costs remain bounded, and the
work remains compatible with Lucas's family and financial obligations.

Pause when results reduce to role-play, the system cannot be evaluated
independently, meaningful progress requires premature major spending, or the
project starts relying on unverifiable claims.
